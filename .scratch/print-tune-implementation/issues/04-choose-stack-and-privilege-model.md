# 确定技术栈、进程边界与管理员提权模型

Type: grilling
Status: resolved
Blocked by: 01

## Question

是否采用 C# / .NET 8 + WPF 构建纯离线单机工具？根据配置 API 的权限事实，确定首版使用单进程按需管理员提权、安装时 elevated，还是 UI 与特权 helper 分离；同时确定目标运行时部署方式、原生互操作策略和避免整个 UI 长期高权限运行的要求。结论需覆盖开发、测试和现场分发约束。

## Comments

- 2026-10-24 用户初选：C# / .NET 8 + WPF；普通权限 UI + 仅特权操作使用的短时提权 helper，不常驻后台服务。
- 阻塞冲突：用户同时要求 Windows 7 / 10 / 11、x86 + x64，而微软明确 .NET 8 不支持 Windows 7。需重新选择“保留 Win7 并调整运行时”或“放弃 Win7 并保留 .NET 8”后才能解决本票据。
- 若 Win7 必须保留，.NET Framework 4.8 可安装于 Windows 7 SP1 x86/x64 并支持 WPF，但 Windows 7 本身已停止支持，现场离线安装和补丁前提需纳入部署验证。来源：https://learn.microsoft.com/en-us/dotnet/framework/get-started/system-requirements
- 2026-10-24 用户复核后选择：保留 Windows 7，V1 改用 .NET Framework 4.8 + WPF，一套主代码覆盖 Windows 7 SP1 / 10 / 11 的 x86/x64；保留普通 UI + 短时提权 helper 的方向。本票据留待后续工作会话正式整理并关闭。

## Answer

V1 采用 **.NET Framework 4.8 + WPF、普通权限主程序、按需启动的短时提权 helper**。不使用 .NET 8，不设置常驻 Windows 服务，也不要求整个 UI 以管理员身份运行。

### 1. 运行时与构建目标

- 主技术栈为 C#、.NET Framework 4.8、WPF；选择理由是覆盖 Windows 7 SP1 / 10 / 11，同时保留 WPF 和 Win32 P/Invoke 能力。
- 提供明确的 `x86`、`x64` 构建和对应发布包，UI 与 helper 必须同架构；不使用 `AnyCPU + Prefer 32-bit` 模糊实际进程架构，不承诺 ARM64。
- 主程序、helper 和核心库统一以 .NET Framework 4.8 为最低运行时。现场安装器/引导程序负责检测运行时；缺失时使用经过验证的离线安装包或给出明确前置安装指引，不在应用内自动联网下载。
- Windows 7 已停止支持，属于用户明确接受的现场兼容范围；其 SP1、系统更新、离线运行时安装和驱动组合必须进入手动部署验收，不能写成与 Win10/11 无差别的支持承诺。

### 2. 解决方案职责边界

首版按职责划分，不预先拆成过多微组件：

- `PrintTune.UI`：WPF/MVVM、打印机选择、原厂首选项窗口、配置包选择、操作编排、状态展示和人工确认；默认 `asInvoker`。
- `PrintTune.Core`：配置包模型、兼容判定、操作状态机、备份计划、错误语义和审计记录；不依赖 WPF，便于单元测试。
- `PrintTune.Win32`：Unicode/W 系列 Win32 互操作、缓冲区、句柄、DEVMODE 深复制、能力查询、Level 8/9 读写与 GDI 测试打印；通过接口接入 Core，禁止 UI 散布 P/Invoke。
- `PrintTune.Elevated`：独立、短时运行的特权 helper，仅执行明确允许的 Level 8 应用/回滚及必要的同层回读；不加载 WPF，不提供通用脚本或任意命令执行能力。
- 测试项目：Core 单元测试使用假 Win32 适配器；集成测试通过同一适配器发现现有虚拟打印机；手动实机验收另留结构化记录。

详细项目依赖、接口签名和日志组件仍在后续架构规格中设计，本票据只冻结职责与权限边界。

### 3. 权限与 helper 调用规则

- 枚举、读取、原厂设置窗口、导出、Level 9 操作和测试打印均在原交互用户的普通 UI 进程中执行，并分别请求最小必要权限。
- UI 不一开始请求 `PRINTER_ALL_ACCESS`。只有实际执行管理操作时才请求相应管理访问；遇到 `ERROR_ACCESS_DENIED` 时展示原因，并由用户明确选择是否提权，不静默反复提权。
- Level 8 应用/回滚可由 UI 直接尝试具备队列管理权限的路径；需要提升时，通过 `ShellExecute`/`runas` 启动同架构 `PrintTune.Elevated`，完成单一事务后退出。无后台常驻进程。
- helper 使用版本化、强校验的请求/响应协议，只允许白名单动作；校验操作类型、目标队列、配置包结构、事务 ID、文件路径和超时，不接受任意命令行脚本、任意 Win32 Level 或通用文件写入。
- IPC 的具体传输在详细架构中选择，但必须限制为同一交互会话/同一用户授权的操作，避免把本机任意进程输入直接当成已授权请求。UAC 不是输入校验的替代品。
- helper 不弹厂商首选项窗口，不执行测试打印，不浏览配置文件，不自行扩大操作范围；把结构化结果交回 UI，由 UI 展示分阶段状态。

### 4. Level 9 用户作用域约束

- **Level 9 始终由原始交互用户进程读写，禁止通过可能切换用户身份的 elevated helper 写入。**UAC 若使用另一管理员账户，helper 的“当前用户”就不再是业务操作用户。
- UI 在执行 Level 9 操作前显示目标 Windows 用户/配置文件含义；服务账户、计划任务账户和其他管理员账户不能混用。
- Level 8 应用前，原 UI 先备份当前交互用户 Level 9，再完成 Level 8 备份与写入；回滚按相反责任边界分别恢复并同层回读。具体事务顺序由后续工作流状态机确定。

### 5. Win32 互操作约束

- 统一使用 W/Unicode API 与 `DEVMODEW`，配置包记录数据形态；不混用 ANSI 字节布局。
- 所有双调用探长度、返回码、`GetLastError`、空 `pDevMode`、缓冲区溢出、句柄释放和同步阻塞集中在 Win32 适配层处理。
- 原生句柄不跨线程共享；阻塞调用不直接占用 WPF UI 线程。取消操作不能假造 Win32 调用已回滚，需按实际完成阶段报告。
- 完整 DEVMODE 深复制与不可信输入边界校验先于任何驱动调用；UI 与 helper 使用同一份 Core 校验逻辑，避免提权路径绕过检查。

### 6. 测试与分发约束

- 自动化分别覆盖普通 UI、模拟提权 helper 和真实 helper 集成路径；至少验证拒绝提权、helper 超时/崩溃、非法请求、架构不匹配、Level 8 失败及 Level 9 不跨用户写入。
- x86/x64 发布包不得混放 helper；安装或便携启动时都做架构与完整性自检。具体安装包技术、代码签名和版本发布流程留待后续发布规格。
- 不因为引入 helper 就把所有 Level 8 操作强制管理员化：已经具备队列 ACL 管理权限的环境应可直接完成，提权是明确的降级路径。
