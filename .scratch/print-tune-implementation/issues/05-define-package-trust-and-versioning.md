# 确定 `.ptcfg` 信任、安全与版本演进策略

Type: grilling
Status: resolved
Blocked by: 01, 02

## Question

首版 `.ptcfg` 要防哪些威胁：仅文件损坏，还是也包括恶意替换、错误分发和敏感元数据泄露？是否需要数字签名/内置公钥验签、是否允许无签名包及如何提示；配置名称、备注、适用型号说明是否可编辑，哪些来源元数据必须只读；格式版本、校验范围、未知字段和向前/向后兼容规则如何定义？

## Comments

- 2026-10-24 用户初选：V1 使用 SHA-256、长度/溢出/结构校验和可信来源提示；数字签名后置。备注与适用说明可编辑，来源元数据只读。
- 本票据尚未正式解决：仍需在后续会话确认校验覆盖范围、格式版本和未知字段规则，并将初选整理为最终答复。

## Answer

V1 将 `.ptcfg` 视为**不可信输入**，使用严格结构与边界校验、受保护内容 SHA-256 和明确的“来源未验证”提示。数字签名不进入 V1；SHA-256 只用于发现意外损坏或非配合式修改，**不能证明发布者身份，也不能阻止会重新计算校验值的恶意替换**。

### 1. 威胁边界与 UI 表述

V1 防护：

- JSON/Base64 截断、损坏、重复字段和异常大小。
- `dmSize + dmDriverExtra` 溢出、实际长度不符、公共头不完整、非法编码及可能拖垮进程/打印后台的异常输入。
- 来源元数据与展示备注混淆、旧阅读器误解新格式、未知必需能力被静默忽略。
- 将未经校验的 DEVMODE 交给驱动或提权 helper。

V1 不宣称防护：

- 能重新生成 SHA-256 的恶意文件替换。
- 恶意发布者、错误客服分发或社交工程。
- 私有 DEVMODE 内容与目标驱动的天然兼容。
- 配置包泄密后的隐私保护；V1 不加密配置包。

导入页固定显示“完整性校验结果”和“发布者签名：未提供/来源未验证”，不得把 checksum 通过写成“文件可信”或“绝对安全”。用户只能从不明来源提示中继续进入兼容检查；结构无效、校验失败或必需能力未知时必须阻断，不能靠确认框放行。

### 2. 受保护区与可编辑展示区的分离

逻辑上分为三类内容，具体字段布局由后续 JSON Schema 票据固定：

- **格式控制**：`formatVersion`、校验算法与校验值。阅读器先严格识别版本，再按该版本规则校验。
- **受保护内容**：完整 DEVMODEW Base64、实际总长度、`dmSize`、`dmDriverExtra`、来源层、驱动身份/版本/环境、导出时间、必要的 OS/进程架构、兼容与扩展声明。它们参与 SHA-256，导入后只读。
- **可编辑展示内容**：配置名称、客服备注、适用型号说明。它们不参与 DEVMODE 兼容判定，不表示实测白名单资格，也不要求因文字修改而重算受保护区校验值。

UI 必须把“用户填写的适用说明”和“程序采集的驱动身份”分开展示。不得根据备注中的品牌、型号、“已验证”等字样调整兼容结论。

受保护内容不可原地编辑；需要变化时通过重新导出或显式格式迁移生成新配置包。展示内容可编辑，并保留原始受保护内容不变。

### 3. SHA-256 的确定性与校验顺序

- 校验覆盖受保护对象的**确定性序列化字节**，而不是依赖原始 JSON 缩进、属性排列或换行；这样合法的美化/序列化不会意外破坏往返校验。
- V1 的确定性规则在 Schema 中固定为：UTF-8、属性名排序、无无意义空白、整数使用十进制、字符串使用统一 JSON 转义；禁止重复键、NaN/Infinity 和含糊数字。所有生产者与消费者共用同一实现和测试向量。
- `checksum` 使用小写十六进制 SHA-256，并显式记录算法与作用域版本，避免未来更换算法时产生歧义。
- 可编辑展示区不纳入该校验；其内容永远不作为安全或兼容依据。数字签名引入时再定义覆盖展示区还是受保护区的独立信任策略，不能把 checksum 当成签名过渡品。

导入顺序固定为：**文件大小/JSON 基础检查 → 版本识别 → Schema 与重复键检查 → 确定性重建及 SHA-256 → Base64 解码与 DEVMODE 长度/溢出/结构检查 → 来源/目标兼容判定 → 目标驱动合并**。任何前序失败都不得继续调用驱动。

### 4. DEVMODEW 与来源元数据

- V1 只接受明确标记的 Unicode `DEVMODEW` 字节形态；不把 ANSI 或本机 `TCHAR` 布局当成相同格式。
- 文件同时记录实际总字节数、`dmSize` 和 `dmDriverExtra`，并验证总长度等于二者之和且不超过解码缓冲区；只复制 `sizeof(DEVMODE)` 或信任文件声明均不合格。
- `source` 使用封闭枚举区分队列默认值与当前用户默认值；跨层恢复是否允许由工作流票据决定，不能由导入器暗中选择。
- 驱动名、真实文件版本、驱动环境/架构缺失时保留“未知”，不得伪造 `0.0.0.0` 参与完全匹配。未知关键身份默认阻断完整私有恢复。
- 队列名、端口和打印机名用于展示/定位提示，不单独作为兼容身份。默认不写入业务票据内容、真实票据数据、Windows 用户名、SID 或不必要的机器标识。

### 5. 格式版本与迁移

- V1 使用整数 `formatVersion: 1`，它表示文件结构及语义的主版本，不与应用发布版本或驱动版本混用。
- 高于已支持版本的文件直接拒绝，提示升级 PrintTune；不得按 V1 尽力解析高版本。
- 未来支持旧版本时，必须通过显式、逐版本、可测试的迁移器转换；迁移后按新格式重新导出并生成新的校验值，保留来源说明。禁止在阅读器里堆叠隐式猜测。
- V1 不承诺把高版本包“降级导出”给旧程序；若未来提供该功能，必须单独定义能力损失并明确提示。
- 应用版本升级不改变已导出包的兼容承诺；驱动支持矩阵与格式版本分别演进。

### 6. 未知字段与扩展

- 根对象、受保护对象和 DEVMODE 描述对象默认拒绝未知字段，防止不同阅读器对安全/兼容语义产生歧义。
- 仅允许在专用 `extensions` 区域放置命名空间化扩展；未知可选扩展可忽略其应用语义，但必须纳入校验、在编辑往返中保留，且不能改变 V1 的兼容结果。
- 使用 `requiredFeatures` 声明理解该包所必需的能力；遇到未知必需能力直接阻断。不得把必需能力伪装成可选扩展。
- Schema 的 `additionalProperties`、扩展命名和保留规则必须与上述策略一致，不能文档严格而代码宽松。

### 7. 签名演进与验收

- 数字签名作为后续独立版本能力设计，需要同时解决私钥保管、签名制作端、公钥更新、吊销/轮换和客服分发，不在 V1 留下“看似签名但实际无验证”的占位按钮。
- V1 测试必须覆盖：校验通过、展示文字编辑后仍可用、受保护内容任意改动后失败、重复键、未知版本、未知必需扩展、Base64 截断、长度溢出、超大输入、ANSI 标记、关键驱动身份未知及 helper 二次校验。
- 安全验收标准是“非法或无法理解的包不进入驱动”，而不是“所有非法包都有可继续的高级按钮”。
